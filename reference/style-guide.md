# Writing Style Guide — 개조식 보고서 문체

All proposal content (SSOT bodies and assembled output) MUST follow this guide.
The Writer drafts against it, the Critic verifies against it (checklist item 7-8),
the Overseer applies it during cross-review, and the output pipeline applies it
to the assembled document during the Full-Document Review gate.

This file is the single source of truth for tone and style. Do not restate these
rules in other files — reference this file instead.

> **적용 범위**: SSOT 본문(Summary / Content / Supporting Evidence)과 최종 출력물.
> 사용자와의 대화, 에이전트 간 보고는 해당 없음.

---

## 1. 종결 규칙 — 개조식 명사형 종결

- 본문의 모든 불릿, 표 셀, 문장은 **명사형으로 종결**: ~함, ~임, ~됨, ~필요, ~예정, ~구축, ~제공, ~확보, ~수행
- 합쇼체(~합니다, ~입니다) 및 평서형 산문(~한다, ~이다) **금지**
- 의문형, 청유형, 감탄형 금지

| 잘못된 예 | 올바른 예 |
|-----------|-----------|
| 이중화 구성을 통해 안정성을 확보합니다 | 이중화 구성으로 가용성 99.99% 확보 |
| 3단계로 나누어 이행할 예정입니다 | 3단계 이행 (파일럿 → 부분 → 전면) |
| KCMVP 인증을 보유하고 있는 제품입니다 | KCMVP 인증 보유 (인증번호 명기) |

## 2. 구조 규칙

- 본문은 **불릿, 표, 다이어그램으로만** 구성. 3문장 이상 연속되는 산문 단락 금지
- **한 불릿 = 한 메시지.** 한 불릿은 최대 2줄
- 불릿 계층은 최대 3단계
- 4개 이상 항목의 비교·나열은 표로 전환
- 중요도는 수사가 아니라 **배치**로 표현: 가장 중요한 항목이 첫 번째 불릿

## 3. 금지 표현

### 3.1 억지 강조 — 강조는 구조와 수치로

| 금지 패턴 | 대체 방법 |
|-----------|-----------|
| "핵심은 ~", "가장 중요한 것은 ~" | 해당 내용을 첫 불릿으로 올리고 키워드만 **볼드** |
| "무엇보다", "특히 주목할 점은", "주목해야 할" | 삭제 — 내용 자체로 전달 |
| "결론적으로", "요약하자면" (본문 중간) | 삭제 — 요약은 Summary 섹션의 역할 |
| "성공적인", "차별화된", "최적의", "강력한" (근거 없는 수식어) | 수치·인증·사례로 대체 |

모든 항목에 "핵심", "가장 중요"를 붙이면 아무것도 강조되지 않음. 한 섹션에서
이런 표현이 1회라도 나오면 위반.

### 3.2 연결어·접속사

- 불릿 첫머리 접속사 금지: "또한", "그리고", "이를 통해", "뿐만 아니라", "아울러", "한편", "더불어"
- 개조식에서 항목 간 연결은 배치 순서와 계층 구조가 담당 — 접속사가 필요하다고
  느껴지면 불릿 구조가 잘못된 것

### 3.3 완곡·의지 표현

| 금지 패턴 | 대체 |
|-----------|------|
| "~할 수 있습니다" | "~가능" + 조건 명시 |
| "~하고자 합니다", "~할 예정입니다" | "~예정", "~계획" |
| "최선을 다해", "적극적으로", "철저히" | 검증 가능한 행동·수치로 대체 |

## 4. 허용되는 강조 수단

- **배치**: 중요한 항목을 먼저
- **볼드**: 한 불릿 안에서 키워드 1개까지
- **표**: 비교 우위는 표의 행으로 보여줌
- **수치**: "가용성 99.99% (연간 장애 허용 52.56분)" — 수치 자체가 강조

## 5. 중복 금지 — Single-Home 원칙

- 하나의 정보(사양, 수치, 주장, 표)는 제안서 전체에서 **정확히 한 곳에만** 존재
- 타 섹션 소유 정보를 인용할 때: 1줄 요약 + `[REF: <ssot-id>]` 참조 — 표나 문단을 복사하지 않음
- 같은 SSOT 안에서도 Summary와 Content 간 문장 재사용 금지 — Summary는 결론과
  수치만, 상세는 Content에만
- 같은 SSOT 안에서 동일한 주장·근거를 두 번 이상 서술하지 않음 — 한 번 말했으면 끝
- 허용되는 유일한 의도적 중복: Executive Summary (전체 요약본의 성격상 허용)

## 6. 예외

다음 경우에 한해 산문·원문 유지 허용:

- **직접 인용**: RFP 원문, 법규·가이드라인 조문, 고객사 공식 표현
- **산문이 관례인 섹션**: 표지 인사말, 회사 소개 등 — `proposal/.bidkit/meta/outline.yaml`에서
  해당 섹션에 `style: prose`를 명시한 경우에만

## 7. 변환 예시 (Before → After)

### 예시 1 — 합쇼체 + 억지 강조 + 접속사

**Before:**
> 당사는 금융권에서 검증된 HSM 솔루션을 제공합니다. 핵심은 안정성입니다.
> 또한 KCMVP 인증을 보유하고 있어 규제 요건을 충족합니다. 이를 통해 고객은
> 안정적인 암호화 서비스를 운영할 수 있습니다.

**After:**
> - **금융권 검증**: 국내 금융권 12개 사 운영 중 [REF: sa-ref-001]
> - 가용성 99.99% (연간 장애 허용 52.56분), Active-Active 이중화 기준
> - KCMVP 인증 보유 (인증번호 KCMVP-XXXX) — 전자금융감독규정 제31조 충족

### 예시 2 — 중복 서술

**Before:**
> 본 시스템은 3단계로 이행합니다. 1단계는 파일럿, 2단계는 부분 적용,
> 3단계는 전면 적용입니다. 가장 중요한 것은 단계별 검증입니다. 즉, 파일럿
> 단계에서 검증을 거친 후 부분 적용으로 넘어가고, 부분 적용에서 다시 검증한 후
> 전면 적용하는 단계적 접근이 핵심입니다.

**After:**
> - 3단계 이행: 파일럿(2개월) → 부분 적용(3개월) → 전면 적용(4개월)
> - 각 단계 종료 시 Go/No-Go 검증 게이트 운영 — 통과 기준은 단계별 KPI 표 참조

### 예시 3 — 타 섹션 데이터 복사

**Before:**
> (비용 섹션에 HSM 장비 사양표 전체를 다시 게재)

**After:**
> - HSM 장비: Luna Network HSM 7 × 4대 [REF: sa-hsm-001] — 사양 상세는 해당 섹션 참조
> - 본 섹션은 도입 비용 산정만 다룸: 장비비, 라이선스, 유지보수 5년 TCO

## 8. 검증 방법 (Critic / Overseer / Full-Document Review)

- 위 1~5 위반은 **Warning** — Critic verdict 규칙상 Warning 1건이면 FAIL이므로
  세션 루프 안에서 자동으로 수정됨
- 금지 패턴은 기계적으로 검출 가능: "합니다", "입니다", "핵심은", "가장 중요한",
  "무엇보다", "또한 ", "이를 통해" 등을 본문에서 검색
- 6번 예외(직접 인용, `style: prose` 섹션)는 위반으로 처리하지 않음
- 조립된 최종 문서(proposal-vN.md)에 대해서는 `playbooks/output/SKILL.md`의
  Full-Document Review가 같은 기준을 문서 전체 단위로 재검증
